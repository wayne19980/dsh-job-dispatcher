# 实战反馈：一天约 30 个后台 worker（2026-11-13）

> 来自一次真实使用：在一个前端 + 演示栈仓库里，用调度台预设完成「多条浏览器端巡演 + 演示数据 + 录屏」的交付，一天派发约 30 个后台 worker。主对话只有只读工具，所有实现与验证都经 `dispatch` 完成。以下为**脱敏后**的观察与需求，供插件迭代参考（项目名、文件路径、端口、dispatch 编号等已移除）。

## 一、时间账

| 类别 | 占比（估） | 典型例子 |
|---|---|---|
| worker 重新发现上下文 | ~50% | 删一行文案前要 grep 全仓、判断组件是否死代码、确认演示副本要不要一起改 |
| 验收（浏览器长巡演 + 重试） | ~25% | 单次三条巡演 ≈ 3 分钟，失败重试再翻倍；一单因此跑到 40 分钟被人工停掉 |
| 双树同步（改两处 + 校验） | ~15% | 每次前端改动都要在主线与演示副本各改一遍并比对 |
| 人肉 round-trip（重启 mock） | ~10% | 改演示数据必须由用户手动重启本地 mock 服务，一天 5 次 |

结论：**改代码本身 < 5%**。

## 二、七个最痛的点

### 1. dispatch 出去的 worker 不可寻址，前提过期后无法纠偏（最痛）

- 在同时启用 Agent Teams 的 profile 里，团队版 `send_message` / `interrupt_agent` 按 teammate 名字寻址，对 dispatch 出来的 worker 报 `active teammate not found`。
- 后果：一个 worker 不知道另一单在它运行期间删掉了它验收依赖的文本断言，每个巡演步骤空等超时；另一个 worker 的工作目录被其它单删掉后卡死。
- 对比：持久 teammate 可以按名字中途纠偏，确实能救回返工。

### 2. 同一个文件被多个 worker 同时写

- 两个热点大文件一天内被 5–6 个 worker 反复写。
- 实际发生过：UI 改动被同步脚本覆盖一次；两个 worker 同时改同一文件导致一方改动丢失；多个单子长时间排队等同一个文件。

### 3. 验收无分级、无预算

- 规则要求「每单都跑类型检查 + lint + 浏览器巡演 + 多视口 + 截图」，删一行字也要数分钟。
- 没有硬超时：被停掉那单跑了 40 分钟，其中约 30 分钟在验收。

### 4. 长任务不可观测

- 只能等最终报告。两次出现「到底还在写还是卡住」的判断困难，只能另派一个只读 worker 去 stat 文件、grep 代码、看端口，才确认「代码已写完、卡在验收」。

### 5. 跨 PID namespace

- 宿主机上的 mock 和前端服务不在 worker 的命名空间里：`ps` 看不到、`kill` 无效、`lsof` 拿不到 pid。
- 改演示数据必须用户手动重启服务，形成「派单 → 等用户 → 再派单」的串行链。

### 6. 项目结构放大所有成本

- 演示前端是主线的物理副本，每次改动要改两处；同步脚本使用 `rsync --delete`，已造成过一次 UI 被回退。
- 这属于项目模板/结构层的问题，不应该由调度插件兜底。

### 7. 环境没有失败保底

- worker 写坏 fixture，且临时目录不持久，无法恢复，只能从进程内存重建，数据保真度受损。
- 缺少「写前备份 / 写后校验」的强制机制。

## 三、对插件的需求（按优先级）

### P0（直接决定一半以上的浪费）

1. **dispatch worker 也应可寻址**：至少支持 `send_message` 纠偏 + `interrupt_agent` 停止；或者把持久 worker 设为默认，`dispatch` 作为 fire-and-forget 专用。
2. **文件写租约**：任务创建时声明 `write_scopes`，运行期对重叠 scope 强制串行（或至少明确告警 + 排队），不能只是 advisory。
3. **结构化进度上报**：worker 每完成一步上报 `{step, files, status}`，Lead 能随时查「它现在在第几步、卡在哪」，而不是只能等最终报告。
4. **验收分级 + 硬超时**：给 worker 一个 `verification: quick|full` 参数（quick = 类型检查 + 关键断言；full = 浏览器/截图/多视口），并设硬超时（如 15 分钟），超时先交代码 + 交接清单。

### P1

5. **断点续跑**：worker 被停后保留 checklist/进度，新 worker 能「接着上次的第 N 步」，而不是靠 Lead 手写恢复 brief。
6. **变更感知注入**：在 worker 每个 step 边界注入环境快照（关键目录是否存在、端口监听、关键文件 sha/mtime），避免「前提过期却不知道」。
7. **宿主执行通道**：允许经审批在宿主执行受控命令（重启 mock/前端、`git status`），或让 Lead 直接拥有只读 shell（大量 round-trip 是因为 Lead 连 `curl` 都没有）。
8. **子任务清单**：一个任务内支持 N 个子项（一次 spawn 处理「删 6 处文案」），减少 spawn 与上下文重建。

### P2

9. **冲突告警**：两个 worker 声明相同 scope 时，创建阶段就提示并建议拆分。
10. **写前备份/写后校验**：对 `data/**`、`*.json` 这类文件，工具层自动备份到会话级持久目录，不依赖临时目录。

## 四、已经能靠流程解决、不必进插件的

- **只读盘点单性价比最高**：先派一个「只读调查 + 出方案」的 worker，再派实现单，返工率明显下降。
- **小改动攒批**：3 单纯文案改动合并成一单能省一半时间。
- **热点文件单所有者**：同一时间只允许一个 worker 写某个热点文件。
- **验收分级**：文案类只跑类型检查 + 文本 grep；交互类才上浏览器巡演。
- **持久 worker 用在长任务**：可中途纠偏的持久成员能明显减少返工。

## 五、路线图（插件侧）

| 版本 | 内容 |
|---|---|
| v1.1 | 可寻址工具（`dispatch_update` / `dispatch_stop` / `dispatch_workers`，唯一命名、不受团队同名工具覆盖）；写租约强制拦截（同 workspace 的 `write_scopes` 重叠直接拒绝并列出冲突单）；Host 重启后 running 条目对账 |
| v1.2 | 结构化进度（Host 监听子会话事件，看板显示当前 step/最近工具/活动时间）；`verification: quick\|full` + `budget_minutes` 注入 brief；`resume_of` 自动拼接上次交接 |
| v1.3+ | 命名持久 worker（own layer over subagents，显式 `agentPreset: standard`）；变更快照注入；自动排队/依赖 |

明确**不归插件管**：跨 PID 的宿主服务控制（需要带审批的独立 host-exec 插件）、双树项目结构、热点文件所有权等流程约束、临时目录持久化。

## 六、一句话结论

瓶颈几乎全在**调度层的可观测性与可纠偏性**，而不是模型能力：worker 干得都不错，但它们看不到彼此、改不了彼此的错，也不该被一个文件串死。优先做 P0 的四项，能直接砍掉一半以上的人力和等待。
